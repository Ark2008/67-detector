# WebSocket: спецификация главного экрана

Соединение открывается на время одной сессии демонстрации, после REST-вызова `POST /sessions` 

Endpoint: `ws://<host>/ws/sessions/{session_id}`

Сервер всегда принимает соединение. Если сессии нет, она уже завершена или `session_id` не UUID — присылает `error` с кодом `session_not_found` и закрывает сокет.

У сессии одно соединение. Пока сессия активна, к ней можно подключиться заново (например, после перезагрузки вкладки): новое соединение получает `session_ready` с текущим `score`, прежнее сервер закрывает.

## Клиент → сервер

Одно сообщение на каждый обработанный кадр видео, даже если рука не найдена — пустой `hands` (обновляет `last_activity_at`). Сообщения текстовые (JSON), бинарные не принимаются.

```json
{
  "type": "frame",
  "timestamp_ms": 1730000000123,
  "hands": [
    {
      "handedness": "Right",
      "score": 0.98,
      "landmarks": [
        { "x": 0.51, "y": 0.42, "z": -0.03 }
        // ... 21 точка, порядок — как в MediaPipe Hand Landmarker
      ]
    }
  ]
}
```

- `hands`: массив длины 0, 1 или 2 — жест «шесть-семь» показывается двумя руками, обе передаются на backend и в CV-модуль.
- `x`, `y` нормализованы [0, 1], `z` — относительная глубина, как отдаёт MediaPipe.
- Частота отправки ограничивается фронтендом до ~15–20 кадров/с.
- Обязательны все поля из примера: `type`, `timestamp_ms` (число ≥ 0), `hands`, у руки — `handedness` (`"Left"` или `"Right"`), `score` (0..1) и ровно 21 точка в `landmarks`, у точки — `x`, `y`, `z`. Лишние поля игнорируются.
- `last_activity_at` пишется в БД не на каждый кадр, а не чаще раза в `ACTIVITY_TOUCH_INTERVAL_SECONDS` (по умолчанию 2 с), чтобы не делать 15–20 UPDATE в секунду на сессию.

## Сервер → клиент

### `session_ready` — подтверждение после установления соединения

```json
{ "type": "session_ready", "session_id": "...", "status": "active", "score": 0 }
```

### `gesture_detected` — жест засчитан (счётчик, звук, анимация на фронте)

```json
{
  "type": "gesture_detected",
  "score": 4,
  "detected_at": "2026-11-05T12:00:03.210Z",
  "cooldown_ms": 1500
}
```

`cooldown_ms` — информативное поле для UI; защита от повторного счёта всегда на сервере (см. ниже).

### `session_state` — смена статуса сессии (например, сервер закрыл по таймауту)

```json
{ "type": "session_state", "status": "timeout", "score": 7, "ended_at": "..." }
```

После `session_state` с `status != "active"` сервер закрывает соединение.

### `error` — ошибка обработки кадра/сессии (соединение не закрывается, кроме `session_not_found`)

```json
{ "type": "error", "code": "invalid_payload", "message": "landmarks length != 21" }
```

Коды: `invalid_payload`, `session_not_found` (сессия уже завершена/не существует — закрывает соединение), `internal_error`.

- `invalid_payload` — сообщение не JSON, бинарное или не соответствует формату `frame`. В `message` — первая ошибка валидации с путём до поля, например `hands.0.landmarks: List should have at least 21 items after validation, not 0`. Такой кадр не попадает в буфер и не обновляет `last_activity_at`.
- `internal_error` — сбой при обработке кадра (CV-модуль или БД). Кадр пропускается, следующие обрабатываются как обычно.

### Коды закрытия сокета

| Код | Когда |
| --- | --- |
| `1000` | После `session_state`: сессия завершена («Стоп» или таймаут). |
| `1008` | После `error` с кодом `session_not_found`, а также когда соединение вытеснено новым подключением к той же сессии. |

## Защита от двойного счёта (анти-дребезг)

Правило — на сервере, не в CV-модуле (см. [architecture.md](architecture.md)):

1. Сервер держит на сессию буфер последних N кадров и передаёт его в `detect_gesture` при каждом новом кадре.
2. Если `detect_gesture` вернул `gesture == "six_seven"` и с момента последнего засчитанного жеста прошло ≥ `COOLDOWN_MS` (константа backend, ориентир 1500 мс) — засчитывается: `sessions.score += 1`, пишется строка в `gesture_events`, клиенту уходит `gesture_detected`.
3. Если жест распознан, но cooldown не истёк — событие отбрасывается без записи и без отправки клиенту.

Уточнения реализации:

- N — настройка `FRAME_WINDOW_SIZE`, по умолчанию 30 кадров (~1,5–2 с при 15–20 кадрах/с). `COOLDOWN_MS` — по умолчанию 1500.
- Cooldown считается по часам сервера. `timestamp_ms` клиента на него не влияет — он нужен только CV-модулю.
- После засчитанного жеста буфер очищается: иначе кадры уже засчитанного жеста остались бы в окне и дали второе срабатывание сразу после cooldown. Кадры, пришедшие во время cooldown, копятся в буфере как обычно — при непрерывных «качелях» очко начисляется раз в `COOLDOWN_MS`.
- Пока cooldown не истёк, `detect_gesture` не вызывается: его результат всё равно был бы отброшен.
- Счёт и событие пишутся в одной транзакции и только для активной сессии: жест, пришедший после «Стоп» или таймаута, не засчитывается.
- Состояние анти-дребезга (буфер и момент последнего жеста) живёт в памяти соединения: при переподключении к той же сессии буфер и cooldown начинаются заново.

## Жизненный цикл соединения

1. Фронт: `POST /sessions` → получает `session_id`.
2. Фронт: открывает WS на `session_id`, запрашивает камеру, начинает стрим кадров.
3. Пока активна — кадры туда, `gesture_detected` обратно.
4. «Стоп»: фронт шлёт `POST /sessions/{id}/stop`, сервер переводит сессию в `stopped`, присылает в сокет `session_state` и закрывает его.
5. Если вкладка закрылась без «Стоп»: сокет рвётся без сообщения, backend по `last_activity_at` закрывает сессию таймаутом (фоновая задача).
6. Если сокет открыт, но кадры не приходят дольше таймаута (например, игрок не дал доступ к камере): фоновая задача переводит сессию в `timeout`, присылает `session_state` и закрывает сокет.

Таймаут — настройка `SESSION_TIMEOUT_SECONDS` (по умолчанию 30 с), проверка идёт раз в `TIMEOUT_CHECK_INTERVAL_SECONDS` (по умолчанию 5 с), поэтому сессия закрывается через 30–35 с после последней активности.

Открытые соединения backend хранит в памяти процесса. Если backend запущен в несколько процессов и «Стоп» попал не в тот, где открыт сокет, клиент получит `session_state` не сразу, а со следующим кадром после очередной записи `last_activity_at` (в пределах ~2 с).
