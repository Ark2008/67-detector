## REST: Frontend → Backend (главный экран)

Общее для всех эндпоинтов:

- Тела запросов и ответов — JSON. Время — ISO 8601 в UTC с суффиксом `Z` (дробная часть секунд — до микросекунд).
- Ошибки — в формате FastAPI: `{ "detail": "<код или описание>" }`. `404` — объект не найден (`detail` — код, см. ниже), `422` — тело или параметр не прошли валидацию.
- CORS: запросы из браузера разрешены адресам из настройки `CORS_ORIGINS` (по умолчанию Vite dev-сервер `http://localhost:5173`).

### `POST /players`

Вход/первый визит. Идемпотентно по имени: если игрок с таким именем уже есть — возвращает существующего.

```json
// запрос
{ "name": "Петя" }

// ответ 200/201
{ "player_id": "uuid", "name": "Петя", "created_at": "2026-11-05T12:00:00Z" }
```

Фронт сохраняет `player_id` в localStorage и дальше всегда попадает на экран демонстрации без повторного ввода имени.

- `201` — создан новый игрок, `200` — игрок с таким именем уже был. Имена сравниваются без учёта регистра; в ответе `name` — в том написании, с которым игрок был создан.
- `name`: пробелы по краям обрезаются, после этого длина должна быть от 1 до 50 символов, иначе `422`.

### `POST /sessions`

Кнопка «Старт».

```json
// запрос
{ "player_id": "uuid" }

// ответ 201
{ "session_id": "uuid", "status": "active", "score": 0, "started_at": "..." }
```

Дальше фронт открывает WebSocket на `session_id` (см. [websocket.md](websocket.md)).

- `404 { "detail": "player_not_found" }` — игрока с таким `player_id` нет. `422` — `player_id` не UUID.
- Если у игрока уже есть активная сессия, она не трогается: создаётся новая, а прежняя без кадров закроется по таймауту.

### `POST /sessions/{session_id}/stop`

Кнопка «Стоп». Идемпотентен: повторный вызов возвращает текущее финальное состояние без создания новой сессии (реализация — [db-schema.md](db-schema.md)).

```json
// ответ 200
{ "session_id": "uuid", "status": "stopped", "score": 7, "started_at": "...", "ended_at": "..." }
```

- Если сессию уже закрыл таймаут, вернётся её итог со `status: "timeout"`.
- Если у сессии открыт WebSocket, сервер присылает в него `session_state` и закрывает сокет.
- `404 { "detail": "session_not_found" }` — сессии с таким id нет. `422` — `session_id` не UUID.

### `GET /ratings`

Экран рейтинга.

```json
// ответ 200
{
  "players": [
    { "player_id": "uuid", "name": "Петя", "total_score": 42, "best_session_score": 12 }
  ]
}
```

Сортировка по `total_score` убывающая, на стороне backend ([db-schema.md](db-schema.md)). При равном `total_score` выше игрок с большим `best_session_score`, затем — по имени.

В рейтинг входят все игроки, включая тех, у кого ещё нет завершённых сессий (у них оба счёта равны 0). Постраничной выдачи нет.

## Backend → CV

Жест «шесть-семь» показывается двумя руками (попеременное движение, как качели), поэтому backend передаёт в CV-модуль последовательность кадров, где в каждом кадре могут быть landmarks обеих рук (0, 1 или 2 руки на кадр — сколько MediaPipe нашло), а не только одной. CV возвращает решение: распознан жест («six_seven») или нет («none»).

Границы ответственности:
- Порог распознавания применяется внутри CV-модуля — CV уже отдаёт финальное решение, backend его не пересчитывает.
- CV не знает про сессии и cooldown — только классифицирует окно кадров.
- Решение «засчитать очко» (cooldown, запись в БД, WS-событие) принимает backend — правило анти-дребезга описано в [websocket.md](websocket.md).
- Backend отвечает за размер скользящего окна кадров, передаваемого в CV.

### Python-интерфейс

```python
def detect_gesture(frames: list[dict]) -> dict:
    ...
```

`frames` — окно последних кадров сессии, от старых к новым, от 1 до `FRAME_WINDOW_SIZE` (по умолчанию 30) элементов. Кадр — то же сообщение `frame` из [websocket.md](websocket.md), только без поля `type`:

```python
{
    "timestamp_ms": 1730000000123,
    "hands": [  # 0, 1 или 2 руки
        {
            "handedness": "Right",  # или "Left"
            "score": 0.98,
            "landmarks": [{"x": 0.51, "y": 0.42, "z": -0.03}, ...],  # ровно 21 точка
        }
    ],
}
```

Возвращает `{"gesture": "six_seven"}` или `{"gesture": "none"}`.

- Данные передаются простыми `dict`/`list`, чтобы CV-модуль не зависел от backend. Backend валидирует кадры до вызова: в CV приходят только кадры правильной формы.
- Функция не хранит состояние между вызовами: всё нужное есть в окне. Окно может быть короче `FRAME_WINDOW_SIZE` — в начале сессии и сразу после засчитанного жеста (см. анти-дребезг в [websocket.md](websocket.md)).
- Backend вызывает её из рабочего потока на каждый кадр, кроме кадров во время cooldown. Исключение из функции клиент получит как `error` с кодом `internal_error`, соединение не закрывается.
- Типы для подсказок описаны в `backend/app/services/vision/base.py`. Пока CV-модуль не готов, backend использует заглушку с той же сигнатурой — `backend/app/services/vision/stub.py`. Реализация выбирается в одном месте: `backend/app/services/vision/__init__.py`.
